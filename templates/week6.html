Project Overview

From a form generator to a full feedback platform

The platform lets an admin describe a topic in plain language, and Gemini AI turns it into a complete feedback form — ratings, multiple choice, yes/no, and open-ended questions — in one call. Every generated form is archived permanently, so its shareable link keeps working no matter how many newer forms get created after it.

Respondents need no account at all: they open the link, answer, and submit. Behind the scenes, a browser cookie paired with a database constraint makes sure the same person can't submit the same form twice — no login required on their end, just on the admin's.

Once responses start coming in, Gemini reads the open-ended answers and scores sentiment, pulls out recurring keywords, and writes a short summary — cached in SQLite so the dashboard never re-analyzes a response it has already seen.

At a glance

  • One database file — forms, responses and the sentiment cache all live in a single SQLite file.
  • Single admin login gates form generation and the dashboard — no per-user accounts.
  • No login for respondents — just a cookie token to stop double submissions.
  • Deployed on Render with a persistent disk so the database survives restarts.
Project Evolution

How the application evolved during development

Three real phases, in the order they actually happened.

Phase 1

JSON forms + per-form CSV files

Every generated form was archived as its own JSON file, and every form's responses lived in a matching CSV. Simple to reason about at first, but the data was scattered across three folders per form (forms, feedback, sentiment_cache) with nothing tying them together relationally.

Phase 2

SQLite integration

Forms, responses, and the sentiment cache were consolidated into one SQLite database (four tables: forms, responses, sentiment_cache, app_meta), queried directly with Python's built-in sqlite3. A one-off migration script imports any old JSON/CSV data so existing shareable links keep working.

Phase 3

AI-powered platform + duplicate protection

Gemini AI became the engine behind both form generation and response analysis — sentiment, keywords, and summaries — surfaced on an interactive Chart.js dashboard. A respondent cookie token plus a database-level unique constraint now blocks a second submission of the same form from the same browser.

JSON/CSV → SQLite Migration

The architectural upgrade that made everything else possible

Replacing scattered files with one relational-shaped database improved durability, consistency, and made duplicate-submission checks possible in the first place.

SQLite database

  • Four related tables in a single app.db file
  • A unique index enforces one response per respondent per form
  • WAL mode for safer concurrent reads/writes
  • One migration script imports all legacy data in one pass
  • Persists across restarts once placed on a Render Persistent Disk

Learning Outcomes

What this project taught me

This project marked a real milestone in turning a prototype into a durable, production-shaped web app. I learned how to migrate from scattered JSON/CSV files to a single relational-shaped SQLite database, design a small schema by hand with plain sqlite3 rather than an ORM, and enforce business rules — like one submission per respondent — at the database layer instead of only in application code.

Integrating Gemini for two different jobs — generating forms and analyzing responses — sharpened my prompt engineering, and thinking through cookie-based duplicate protection (without requiring respondent accounts) taught me a lot about designing for anonymous users. Deploying to Render also meant reasoning carefully about what "persistence" actually requires: a database file alone isn't enough without disk that survives a restart.
